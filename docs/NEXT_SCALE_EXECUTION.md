# Next scale execution: reliability before another full comparison

The six-world scale-v2 campaign is terminal: all six slots failed during fresh Hermes startup on day 3, before any skill update. Its execution sources, failed prefixes, unknown-usage reservations and cleanup limitations remain frozen. A host reboot subsequently interrupted the surviving original scale-v1 learner; that is separate evidence and cannot complete either comparison. No failed slot is resumed or replaced.

## Intended research endpoint

Keep the original comparison scope: three fresh paired seeds, four enterprises and twelve employee agents per world, the native MiroFish/OASIS actors and fixed Persona cohorts, twenty action days plus settlement, and matched Hermes execution for SkillOpt and no learning. Evaluate prospective deployed skills on the registered fixed task denominator, retaining all employees and all update boundaries. Native demand outcomes are secondary. A valid result may show zero adoptions or no gain; a partial set of successful worlds is insufficient.

## Startup qualification

The new opt-in startup journal observes imports, sandbox setup, AIAgent construction, meter/transport setup and READY. It changes neither the startup allowance nor task timeout and is not a reliability fix. The full future campaign must enable it equally for both arms and optimizer replays, and register its source hashes.

Before another full run, use a separately frozen startup-only qualification with three sequential fresh initializations followed by three batches of two (nine fixed slots total). Each initialization exercises the pinned Hermes source, evaluation configuration and real bubblewrap sandbox, requests no employee work, and performs no learning or actor simulation. Preserve every failed attempt. Keep the existing 150-second startup deadline and a fixed 30-second owned cleanup allowance. Declare the exact resource limits and failure policy before dispatch; no retries, replacement slots, timeout increase or selecting successful attempts after inspection.

The qualification must establish a no-inference boundary before it is run. A parent that never writes a work request, an invalid credential or a missing READY receipt alone does not prove zero network/model usage during initialization. Audit constructor behavior and enforce an explicit boundary; document any resulting difference from deployment startup. Record source/dependency hashes, stage timestamps, process and namespace identities, resource controls, host pressure and cleanup evidence. Cache state is observed, not controlled: do not drop host caches. Passing nine starts establishes only this bounded component result, not six-world or long-horizon reliability.

## Resource containment and process ownership

Bubblewrap confines employee commands and files. Hermes imports and agent construction execute outside that sandbox. Resource controls must encompass the world/startup controller, native worker and all descendants. OASIS actor processes descend from the shared MiroFish service; that service requires its own resource envelope and cleanup chain, independently of per-world units. A systemd user unit can provide a new owned cgroup, subject to fresh kernel readbacks on the current boot.

A harmless probe on the previous boot verified memory.max, memory.swap.max, pids.max and cpu.max; the requested I/O weight had no kernel file and was not effective. CPU/RAM/PID limits contain our use; they do not reserve resources against other workloads. No user-mode I/O isolation or storage-latency guarantee is established. Do not kill, reprioritize or move unrelated processes. A fresh harmless probe has now revalidated these four controls after the observed host reboot; its selected receipts were independently reviewed. See [the resource observation](startup-resource-controls-v1.json). This does not qualify the larger limits proposed for native startup, or any workload capacity.

The existing scale-v2 supervisor treats Popen.pid as the native root and requires a direct world-parent relationship. A systemd-run control client is not that native root. Future unit-aware supervision must separately bind the launcher and actual MainPID using the unit name, InvocationID, ControlGroup, boot identity, PID/start ticks/UID, command and working directory, with direct cgroup membership checks. Preserve the existing Computer-to-Hermes private pipes. Never reuse the old auditor to certify a changed ownership model.

Cleanup evidence must cover the owned cgroup and descendant process identities as well as any bound native sandbox/socket. An empty cgroup does not alone prove alias removal; a missing startup journal does not prove either zero usage or successful cleanup. Interruptions, OOM events, deadlines, missing receipts and provider failures keep explicit dispositions and reservations. A host boot change ends old process lifetimes but does not manufacture missing terminal receipts.

## Full follow-up contract

After the component evidence is reviewed, freeze a new full campaign and auditor before dispatch. Use all six fresh slots and the original scientific denominator. Choose a lower fixed concurrency from the qualified resource envelope, with a fixed counterbalanced ordering. Scheduling may control contention; it does not reduce the number of enterprises, employees, sessions or required pairs. Declare wall-time and usage ceilings that include that schedule and retain missing/failed worlds in the result. Do not mix original, scale-v2 and future outcomes.

The next execution should make startup and cleanup failures diagnosable and bounded while keeping the learning comparison intact. Passing tests, publishing this plan or completing the startup qualification does not finish the active research goal.
