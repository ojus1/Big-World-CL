# Optional Hermes startup observations

This future-run diagnostic records where a fresh employee worker reached before startup failed. Enable `hermes_startup_observability: true` in an experiment configuration, or pass `hermes_startup_observability=True` to `execute_case`. The default is false and omitted from the public configuration; existing executor keyword signatures and model behavior remain unchanged when disabled. Online work and learning replays receive the same option. Historical calibration and transfer wrappers inherit it from the source configuration and preserve it in their own manifests.

Each owned computer gets a private `startup/manifest.json`, `parent.jsonl`, and `worker.jsonl`. The manifest binds an opaque attempt ID, `startup-observation-v1`, and hashes of the journal helper, worker, and computer sources. The parent records the PID returned by `Popen`, plus Linux process start ticks, UID, and boot identity when observable. Identity lookup failures retain the PID and an explicit class-only error; they never establish that a process exited. A worker must match the expected new attempt ID before appending. Failed initialization cannot append to an older attempt's journal.

The worker records fixed before/after stages around heavy Hermes imports, registry setup, sandbox creation, agent construction, budget and transport installation, and the native filesystem probe. `worker_entered` precedes the heavy imports, but follows Python and the small standard-library journal helper. `ready_write_attempt` and `ready_write_returned` describe writing the ready message. The parent separately records `ready_received`, `run_request_write_attempt`, and `run_request_write_returned`. The last two describe the local pipe write and flush, not a physical model dispatch or a complete provider receipt. Exceptions contain only their class; no prompts, environment values, command arguments, provider messages, credentials, or socket paths enter these records. Existing private native logs retain their existing behavior.

The opt-in startup timer includes observer setup. Observation time is subtracted from the existing startup wait, and a late ready message cannot gain a fresh timeout. The existing maximum startup allowance is 150 seconds (or the smaller task allowance). Parent request-write observations also consume the original task timeout; an already expired deadline cannot initiate a request write. Journals use flushed writes without `fsync`; they add diagnostic overhead and have no host-crash durability guarantee. Ordinary filesystem operations themselves have no hard latency bound. If they overrun, the deadline is checked after they return; this is not a guarantee that a blocked host filesystem can be interrupted at the deadline. I/O failures are retained as class-only observation errors in memory and in later journal/returned runtime diagnostics where possible. They do not introduce retries, change adoption, relax accounting, or grant additional time.

A missing/partial journal, missing ready message, or parent pipe-write observation cannot prove zero model usage. A timeout before the parent sends the work request identifies the parent-side startup phase; auxiliary startup/network work and the exact reason for a stall still need separate evidence. `usage_known` and `cleanup_known` remain false in observation summaries. This diagnostic neither establishes descendant cleanup nor changes any frozen auditor or acceptance rule, and it cannot rescue historical failed worlds.

Offline validation:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -S -m unittest lifespan.tests.test_startup_observability -q
```

Tests use deliberately missing imports, strictly fake Hermes dependencies, deterministic simulation callbacks, and harmless short Python child processes. They cover stage ordering, source/attempt/process identity, default omission, online/replay propagation, delayed/crashed startup, failed launches, missing identities, journal I/O failures, stale-manifest refusal, deadline overhead, late ready messages, and secret-canary exclusion. These fixtures are not native benchmark or reliability evidence. No provider request, Hermes agent launch, or dependency installation is part of this test command.
